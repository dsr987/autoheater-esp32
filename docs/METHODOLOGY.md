# METHODOLOGY.md — как протокол был расшифрован

Хроника реверса протокола отопителя по логам Logic 2. Пишется как памятка себе:
когда добавятся новые логи (ошибки, фаза продувки), действовать по этой же лесенке.

## 1. Физика до байтов

Скорость не выбирается по вкусу — выводится из данных:
- минимальный интервал между фронтами = длительность одного бита;
  104 мкс -> 9600 бод (208 мкс -> 4800, 40 мкс -> 25000).
- независимая проверка: межбайтовая пауза внутри кадра оказалась ровно 1,032 мс
  = 10 битовых интервалов, т.е. байты идут подряд без пауз. Совпадение трёх
  независимых метрик (края битов, межбайтовая пауза, успешное декодирование)
  закрывает вопрос навсегда.

**Ловушка:** чужой контекст (известный afterburner-протокол на 25000) тянули
к нашей печке. Правило: сначала измерить, потом вспоминать.

## 2. Нарезка потока на кадры — по статистике пауз

Гистограмма пауз между соседними байтами оказалась бимодальной:
- ~1,0 мс — внутри кадра (байты подряд);
- ~90-100 мс — между кадрами (мастер выдерживает паузу).

Порог между горбами (в декодере — 1,5 мс) рвёт поток на посылки автоматически.
Внимание к грабле: порог ниже межбайтового интервала режет кадр на отдельные
байты (эта ошибка была сделана и найдена на логе 8).

## 3. Структура кадра подсказана данными

- В начале посылок стабильно видны 0xA5 и 0xA0 — два отправителя (мастер/слейв).
- Байты 3-4 почти всегда 00 01 / 00 04 / 00 05, а хвосты бывают ровно 1, 4 и 5 байтов.
  Это поле LEN: протокол с самоописывающейся длиной.
- Гипотеза формата [SYNC][CMD][LEN16 BE][DATA][CRC] сразу проверяется на всём
  корпусе кадров: если формат верен, все кадры «собираются» без остатка.

## 4. CRC проверяется, а не угадывается

Брутфорс по таблице всех CRC-8 (полиномы, init, xorout, отражение) на корпусе
кадров дал единственный вариант, сходящийся на ~99,5 % кадров: CRC-8/MAXIM
(полином 0x31, LSB-first 0x8C, init 0x00 — семейство Dallas 1-Wire).
Случайное совпадение на сотнях кадров исключено.

Битые кадры — не мусор, а доказательства: одиночный сбой бита в LEN (0x01 -> 0x21)
ловится именно нашей CRC, а печка при этом ответила правильно (расшифровала
битый запрос как чтение 0x10).

## 5. Семантика: значения, которые узнают себя

- 00 00 7A 44 (float32 LE) = 1000.0 — круглое число ватт.
- E3 22 5B 41 = 13,39 — диапазон бортовой сети.
- Счётчик с темпом 1,7-4,6 в секунду, тикающий только в рабочих фазах и
  растущий вместе с мощностью — дозы насоса.
- Номера, меняющиеся синхронно с описаниями пользователя («свеча», «загорелось»),
  — машина состояний.

## 6. Дифф-анализ: событие -> изменившийся байт

Рассказ пользователя о кнопках — бесплатная разметка лога. «Нажал стоп» ->
ровно три записи 0x03=0 в этот момент. Каждое совпадение = подтверждение
семантики. Так найдены: старт (0x02=0 x3, 0x03=1), стоп (0x03=0 x3),
мощность (0x01, float32, ватты).

## 7. Проверка на независимых данных

Каждый вывод гоняется минимум по двум логам. Именно так:
- найдена собственная ошибка (заголовок 4 байта, а не 5) — по сбою парсинга на втором логе;
- снята гипотеза «0x0C = уставка температуры» — второй лог показал, что это номер шага;
- открыто явление «пульт переписывает мощность каждый цикл» (записи 0x01 с
  интервалом ровно в цикл опроса без нажатий).

## 8. Цикл исполнения — главный ингредиент

Реверс = не один инсайт, а 2-3 десятка коротких итераций «гипотеза -> скрипт ->
фейл -> правка» за час. Каждый шаг тривиален; ценность в том, чтобы их
действительно выполнять, а не описывать. Без обратной связи от данных ошибки
не отсекаются, а накапливаются (пример: гипотеза 25000 бод дожила до конца чужого
разбора, потому что её никто не проверил на битовых интервалах).

## Что осталось неоткрытым (для будущих логов)

- фаза продувки после стопа: шина мертва, нужен ESP32-мастер с тихим опросом;
- словарь кодов 0x0B (сейчас известен только 0xFF = норма);
- регистры 0x02 (запись), 0x04, 0x05, 0x23, 0x66;
- сброс 0x10 между сессиями (23598 / 31657 / 32996 без монотонности).

# Версионирование и выпуск Autoheater ESP32

## Версия

Каноническая версия прошивки находится в `firmware/app/app.cpp` в маркере `CHANGELOG_VERSION`. Формат — `MAJOR.MINOR.PATCH`.

Каждый PR в `main` должен иметь ровно одну метку `release:*` и раздел `## Changelog` с одним или несколькими пунктами. Автоматизация обрабатывает только PR, который действительно слит в `main`, и ищет PR, связанный с точным SHA завершившейся сборки.

| Метка | Значение | Пример |
|---|---|---|
| `release:patch` | Исправление без новых возможностей | 0.1.0 → 0.1.1 |
| `release:minor` | Совместимое расширение | 0.1.0 → 0.2.0 |
| `release:stable` | Первый стабильный релиз из beta | 0.1.0 → 1.0.0 |
| `release:major` | Несовместимое изменение после 1.0.0 | 1.2.3 → 2.0.0 |
| `release:none` | Документация, исследование, CI без обновления прошивки | версия без изменений |

В beta-версии `0.x.y` метка `release:major` запрещена: для первого стабильного выпуска используется `release:stable`.

## Что происходит после слияния PR

1. Успешная сборка на `main` запускает post-merge workflow.
2. Workflow получает связанный с commit PR и проверяет единственную метку релиза и непустой `## Changelog`.
3. Для `release:none` workflow завершает обработку без изменения файлов, версии или служебного состояния. Создание служебной ветки/PR и токен не требуются.
4. Для настоящего релиза (`release:patch/minor/major/stable`) `tools/release_automation.py` обновляет маркеры версии в `app.cpp`, добавляет пункты в changelog-блок и записывает обработанный PR в `.github/release-automation/state.json`.
5. Эти метаданные отправляются в отдельную ветку и оформляются PR с меткой `release:none`; затем PR сливается автоматизацией. Повторная обработка одного PR не повышает версию повторно.
6. Workflow публикации скачивает бинарник именно из завершившейся сборки и создаёт GitHub Release только если версия в `app.cpp` изменилась относительно родительского commit. Обычные изменения документации и CI не создают фиктивный релиз.

## Требуемый секрет для настоящих релизов

Для автоматического обновления метаданных при `release:patch/minor/major/stable` в Settings → Secrets and variables → Actions создайте `RELEASE_AUTOMATION_TOKEN` — fine-grained PAT для этого репозитория с правами Contents: Read and write и Pull requests: Read and write. Он нужен для отправки ветки, создания PR и его слияния. `GITHUB_TOKEN` не запускает новый push-workflow для собственного коммита, поэтому здесь требуется отдельный токен. Не записывайте токен в файлы репозитория.

Для PR с `release:none` этот секрет не нужен: автоматизация не изменяет репозиторий и не пытается создать PR.

## Безопасность и ограничения

- Workflow использует код из доверенной ветки `main`, а не запускает скрипты из произвольной ветки PR с привилегированным токеном.
- Состояние содержит номера обработанных релизных PR и служит защитой от повторного повышения версии.
- Автоматическая компиляция не подтверждает электрическую совместимость и корректность будущего протокола отопителя.
- Если PR не имеет ровно одной метки `release:*` или корректного `## Changelog`, автоматизация завершится ошибкой вместо угадывания типа релиза.

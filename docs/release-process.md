# Версионирование и выпуск Autoheater ESP32

## Версия

Каноническая версия прошивки находится в `firmware/app/app.cpp` в маркере `CHANGELOG_VERSION`. Формат — `MAJOR.MINOR.PATCH`.

Каждый PR в `main` должен иметь ровно одну метку `release:*` и раздел `## Changelog` с одним или несколькими пунктами. Автоматизация обрабатывает только PR, который действительно слит в `main`, и ищет PR, связанный с точным SHA завершившейся сборки.

| Метка | Значение | Пример |
|---|---|---|
| `release:patch` | Исправление без новых возможностей | 0.1.0 → 0.1.1 |
| `release:minor` | Совместимое расширение | 0.1.0 → 0.2.0 |
| `release:stable` | Первый стабильный релиз из beta | 0.1.0 → 1.0.0 |
| `release:major` | Несовместимое изменение после 1.0.0 | 1.2.3 → 2.0.0 |
| `release:none` | Документация, исследование, CI без обновления прошивки | версия без изменений |

В beta-версии `0.x.y` метка `release:major` запрещена: для первого стабильного выпуска используется `release:stable`.

## Что происходит после слияния PR

1. Успешная сборка на `main` запускает post-merge workflow.
2. Workflow получает связанные с commit PR и проверяет единственную метку релиза и непустой `## Changelog`.
3. `tools/release_automation.py` вычисляет новую версию, обновляет маркеры в `app.cpp`, дописывает пункты в changelog-блок и записывает обработанный PR в `.github/release-automation/state.json`.
4. Изменения метаданных отправляются в отдельную ветку и оформляются PR с меткой `release:none`; затем PR сливается автоматизацией. Повторная обработка одного PR не повышает версию повторно.
5. Workflow публикации скачивает бинарник именно из завершившейся сборки и создаёт GitHub Release только если версия в `app.cpp` изменилась относительно родительского commit. Обычные изменения документации и CI не создают фиктивный релиз.

## Требуемый секрет

В Settings → Secrets and variables → Actions создайте `RELEASE_AUTOMATION_TOKEN` — fine-grained PAT для этого репозитория с правами Contents: Read and write и Pull requests: Read and write. Он нужен для отправки ветки, создания PR и его слияния. `GITHUB_TOKEN` не запускает новый push-workflow для собственного коммита, поэтому здесь требуется отдельный токен. Не записывайте токен в файлы репозитория.

## Безопасность и ограничения

- Workflow использует код из доверенной ветки `main`, а не запускает скрипты из произвольной ветки PR с привилегированным токеном.
- Состояние содержит номера обработанных PR и служит защитой от повторной обработки.
- Автоматическая компиляция не подтверждает электрическую совместимость и корректность будущего протокола отопителя.
- Если PR не имеет ровно одной метки `release:*` или корректного `## Changelog`, автоматизация завершится ошибкой вместо угадывания типа релиза.
